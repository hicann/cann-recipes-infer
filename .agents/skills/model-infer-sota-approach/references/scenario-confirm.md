# 确认推理场景与性能目标（操作细则）

供主 agent 在步骤 1 确定优化场景、目标和验收口径。先复用任务、配置与已有记录，缺失或冲突的事项再向用户确认；推理与采集由后续 subagent 执行。

## 原则

- **先调查后确认**：从仓库收集候选场景，依据调查结果确认待决事项。
- **集中确认**：相关待决事项合并询问，沿用已明确的信息与授权。
- **前置条件优先**：本流程基于已有可运行 baseline；缺失时先建立基线。

## 1. 调查候选场景

从仓库收集，整理成候选清单：

- **模型目录 `models/<model>/`**：
  - 当前默认场景：框架部署检查启动命令的 `--yaml`，独立部署检查模型目录 `infer.sh` 中指定 YAML 的变量。
  - `config/*.yaml` —— 结合实际配置、权重信息和推理入口确认卡数、并行、量化与阶段；文件名仅作定位线索。
  - `README.md` —— 推荐场景说明。
- **已有产物**：`progress.md`、`optimization-analysis/`、`agentic/baseline/baseline_metadata.json` —— 核对已有基线、已确认场景和优化进度；优先使用 `progress.md` 中的模型、权重与部署配置作为场景默认值。

每条候选记录包含 `{YAML 名, phase, 卡数, 并行, 量化, 是否已有 baseline}`。

## 2. 前置条件检查

确认模型已完成部署适配、可按目标部署模式运行，且已有精度可复现的 baseline，或具备现场采集条件。

**条件未满足时**（代码缺失 / 无法运行 / 无可用基线）：向用户说明阻塞点，先通过 `model-infer-migrator` 或 `model-infer-optimize` 阶段 0 建立基线，再继续本流程。

## 3. 向用户确认待决事项

核对以下信息，只向用户确认未决项：

- **Q1 推理场景**：沿用指定场景；未指定时结合入口与候选 YAML 推荐配置，明确阶段、卡数、并行和量化。
- **Q2 优化重点**：decode 单步时延 / prefill 吞吐 / 长序列 / batch·并发 / 整体，用于确定 profiling 采集阶段和候选分析方向。
- **Q3 精度 / 功能判定口径**：沿用已有参照、指标与达标线；缺失时按模型与优化类型提出建议，见 [`scenario-setup.md`](scenario-setup.md)。
- **Q4 性能目标（可选）**：记录 TPOT、吞吐或 E2E 时延的数值目标；未指定时标明“无固定数值目标”，按任务范围探索性能改进，不阻塞后续流程。
- **Q5 输出归档目录**：沿用指定目录，未指定时默认 `optimization-analysis/<case>/`。

## 4. 未指定具体场景时

用户仅提出模型优化或提速需求时，结合当前默认入口、README 与已有记录推荐场景；影响优化方向的取舍交用户确认。

## 5. 确认并传递场景

确认后把结果整理成**场景定义**：

- 模型 / case、代码目录、推理入口
- 选用 YAML（标明 phase / 卡数 / 并行 / 量化）
- workload 侧重
- 精度 / 功能判定口径
- 性能目标（或标"可选"）
- 输出归档目录
- `progress.md` 路径：优先使用调用方指定文件，否则使用模型 `agentic/progress.md`，作为 `<progress_path>` 下传。

场景定义作为步骤 2 `scenario` subagent 的输入，用于构造可复现输入、运行基线并保存 `scenario.md`（见 [`scenario-setup.md`](scenario-setup.md)）。本步仅确认场景，推理执行交步骤 2，Dashboard 在候选发现完成后初始化。

## 输出

已确认的场景定义，供 scenario subagent 使用；前置条件结论（满足 / 需先建立基线）。
