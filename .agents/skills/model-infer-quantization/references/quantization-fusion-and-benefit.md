# 融合算子兼容性与量化收益判断

## A. 融合算子兼容性

### A.1 兼容性分级

| 等级 | 含义 | 默认动作 |
| --- | --- | --- |
| A | 量化主线算子 | 保留融合算子，并接入量化输入和 scale |
| B | 可与量化共存，但通常不承载主量化语义 | 输入 dtype/layout 契约仍满足时保留 |
| C | 需要量化友好替身或 post-load 结构融合 | 先改造周边链路，再判断性能 |
| D | 大融合子图或模型专属融合契约 | 先检查契约，不预设全量量化兼容 |

评估目标版本的输入输出契约，尤其是大融合子图的输出 dtype、cache 布局和配套 scale。即使 FA core 可以保留，仍需核对 QKV、cache 和 prolog。若 attention 保持 BF16，仅其相邻投影或 MLP/MoE 被量化，收益按实际覆盖范围评估。

## B. 量化收益判断

### B.1 收益评估指标

初评估用已有证据估算收益空间。验证时报告端到端与显存实测，需解释偏差时再结合算子和通信数据。

| 口径 | 主要证据 | 判定方式 |
| --- | --- | --- |
| 理论预期 | 量化对象、权重/Cache 体积、计算访存比、batch/seq/并行形态 | 判断量化方案本身是否具备权重带宽、KVCache 带宽、MoE/MLP 计算或访存收益空间 |
| 端到端收益 | 关闭 profiler 的 benchmark JSON 或日志 | 记录 Prefill、Decode、吞吐；分别对比量化前最新基线、原始基线和同条件 BF16 补跑，输出阶段收益、累计收益和同条件收益 |
| 显存收益 | benchmark 元数据、NPU 显存日志、部署卡数 | 记录峰值显存、权重显存和部署卡数变化；显存收益可以独立成立，不等价于低时延收益 |
| 算子级收益 | `op_statistic.csv`、`kernel_details.csv` | 用算子调用变化定位执行路径，在相同工况下对比对应计算链的耗时，判断局部收益或损耗 |
| 非量化瓶颈解释 | `communication.json`、trace、rank tail、编译缓存状态 | 只用于解释端到端收益为何与理论或算子收益不一致 |

### B.2 计算、通信与显存分账

- 固定执行模式、batch、序列长度、并行形态和 KV 策略。有同工况 BF16 profile 时，用量化覆盖部分在基线中的耗时占比估计端到端收益空间，再考虑 dispatch 变化及额外的 quant/dequant 开销。BF16 分发后本地量化可加速 expert 计算，但不会减少该次通信载荷。
- eager 与图模式的收益方向可能不同。结合 kernel 耗时、通信及 host 调度判断原因；仅凭方向变化无法区分这些影响。
- 以 BF16 权重字节为基准估算：`量化后权重 ≈ 原权重 × (1 − 覆盖比例 + 覆盖比例 × 位宽比) + scale 等元数据`。覆盖比例按权重字节计，混合位宽按组分别估算。单卡峰值还要分开核算 KV cache、激活、GMM workspace 和通信缓冲；权重变小后，其他项仍可能导致 OOM。

### B.3 收益证据

- **可作为明确量化收益证据**：在相同部署、负载及其他优化条件下，对比 BF16 与量化方案，或对比不同位宽方案（如 W8A8C8 vs BF16、MoE W4A8 vs W8A8）。
- **可作为量化绝对性能证据**：只给量化 benchmark，或对照中同时改变 MTP、perfect eplb、AFD、服务框架、图缓存等前提时，只能说明量化版本在该组合配置下达到绝对性能目标，不能单独宣称量化 speedup。
