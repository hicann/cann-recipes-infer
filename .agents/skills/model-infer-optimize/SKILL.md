# 模型端到端优化技能

## 概述

本技能编排三个 subagent（model-infer-analyzer / model-infer-implementer / model-infer-reviewer）对目标模型按阶段执行 NPU 推理优化。

```
阶段 0: 模型分析与建立基线
阶段 1: 并行化改造（多卡部署时）
阶段 2: KVCache + FA
阶段 3: 融合算子
阶段 4: 量化适配改造（如阶段 0 已完成量化初评估且用户启用）
阶段 5: 图模式适配
阶段 6: 优化总结
```

每个优化阶段遵循统一流程：分析 → 用户确认 → 实施 → 独立验证 → 阶段总结。已获明确授权的方案沿用原确认。

---

## 重要原则

- **按阶段闭环推进**：按下述阶段顺序执行，通过验收并完成总结后进入下一适用阶段。已有分析、方案或验收结果经核对仍适用于当前代码和配置时可复用；已验收完成或不适用的阶段记录依据后跳过。
- **保持模型完整性**：不为通过验证而简化模型实现、删减功能或降低优化标准
- **主 agent 只做编排**：主 agent 负责派发 subagent、呈现报告、用户确认，不直接修改模型代码或自行实施优化。FAIL 后必须派发 implementer 修复，不能自己改代码
- **implementer 自验证检查**：派发 reviewer 前，核对 progress.md 中的代码加载、适用的编译检查、推理与输出证据是否覆盖本轮改动，并与记录的环境一致。缺失或矛盾时由 implementer 补齐；修复轮复测受影响的路径。
- **验证前提检查**：任何验证结果的前提是被测代码确实被执行。验证前先确认修改后的代码被加载和走到（如检查日志中的模型路径、关键优化标记）
- **异常把控**：主 agent 核查 subagent 报告的依据；存在异常或关键证据不足时，要求调查并补齐后再验收。已确认不满足验收标准的结果按 FAIL 处理，即使 reviewer 报告 PASS。文本生成出现相对基线新增的重复退化、乱码、异常空输出或全 EOS 时，定位原因后再验收。
- **subagent 派发规范**：沿用各阶段模板，给出本轮任务范围、progress.md 路径、所用 skill 和输入产物位置；必要时补充影响执行的上下文。共享状态以 progress.md 为准。
- **方案确认**：呈现推荐方案、依据和待决事项，沿用已有授权；新增取舍或超出授权的方案变更由主 agent 向用户确认，subagent 将待决事项返回主 agent。

### 共通验证与阶段收口

- reviewer 独立验证本轮改动，可复现和诊断问题、准备测试文件；模型实现的修改交 implementer。
- FAIL 时由 implementer 修复、reviewer 复验；需要改变方案时返回分析与确认。修复停滞时，由主 agent 汇总证据与阻塞点，按授权决定继续、回退或停止。
- 精度达标但性能未提升时，交 analyzer 检查部署配置、前置处理、测试方法和 NPU 利用率等，提出保留、调整或回退的建议。
- 性能同时记录相对前一有效版本的阶段增量和相对原始基线的累计变化，附测试条件；部署规模或负载变化时分别说明。
- 主 agent 每阶段汇总并向用户呈现结果；继续推进与提交分别按用户决定或已有明确授权执行。更新当前状态后归档工作区，再进入下一阶段。

## 共享状态文件

> **agent 产物位置约定**：所有 agent 流程产物（progress.md / progress_history.md / optimization_report.md / baseline/ 等）统一归入模型目录下的 `agentic/` 子目录，模型根目录只保留模型本身的代码、配置与入口（modeling / config / requirements / README，独立部署另有 infer.py 与 infer.sh）。下文中所有 `progress.md` / `baseline/` 等裸引用均指 `{model_dir}/agentic/` 下的同名文件。

`{model_dir}/agentic/progress.md`：常驻区（模型信息、当前方案、基线与进度概览）+ 工作区（当前阶段记录）。初始模板见 `templates/progress_template.md`。

`{model_dir}/agentic/progress_history.md`：历史归档。优先读取当前状态，按需定位并读取相关历史；总结时汇总所需记录。

**读写规则**：阶段 0 由 analyzer 初始化常驻区，后续由主 agent 维护当前确认方案、基线引用和进度概览；原始基线保留。工作区由各 subagent 追加，写入前先读取现有内容。

**阶段推进**：阶段验收或回退、跳过的决定收口后，主 agent 将后续仍需使用的方案、配置和基线引用更新到常驻区，再在仓库根执行 `python3 .agents/skills/model-infer-optimize/scripts/archive_progress.py {model_dir}/agentic/progress.md`，归档并清空工作区。阶段 0 不归档。

## 工作流程

### 阶段 0：模型分析与建立基线

#### 0.1 信息收集

先从任务、已有配置和 progress.md 获取以下信息，缺失或存在冲突时由主 agent 向用户确认：
- **模型工作目录**：模型代码所在路径（如 `models/xxx`）
- **模型来源**：HuggingFace 链接、本地权重路径、或仓库内已有
- **权重路径**：权重所在位置（可后续补）
- **部署模式**：默认 `框架部署`（cann-recipes-infer 仓库推荐）。仅在用户明确表示要在仓外使用 / 不接框架时改为 `独立部署`
- **验收口径**：目标负载、精度参照、指标及达标线，后续验证沿用；可结合阶段 0 分析补齐

#### 0.2 启动分析 subagent

派发 model-infer-analyzer：

```
工作目录: {model_dir}
任务: 模型架构全面分析
模型来源: {HuggingFace 链接 / 本地路径 / 仓库内已有}
分析内容:
  - 架构类型（LLM / MoE / Diffusion / 多模态）
  - 按实际架构拆解网络；LLM 覆盖 Embedding → Transformer Blocks → Output Head 和 Prefill / Decode 分支差异
  - 关键模块：Attention 类型（GQA/MHA/MLA）、FFN/MoE 结构、特殊模块。架构识别必须基于实际 config 值（config.json / model.config），不能仅从代码类定义推断——注意可配置开关（如 use_mla、n_routed_experts）
  - 运行环境：通过 `asys info -r=status` 确认 NPU 型号（运行前需 source CANN 包路径：source /usr/local/Ascend/ascend-toolkit/latest/bin/setenv.bash）；通过 `npu-smi info` 确认单卡 HBM 容量，记录量化模式、执行模式、部署卡数
  - 模型当前状态：确认代码是否存在且可运行（框架部署看是否注册到 support_models.py 并能用 executor/scripts/infer.sh 拉起，独立部署看模型目录 infer.sh 能否跑通）、agentic/baseline/baseline_metadata.json 是否存在。报告状态（可运行/不可运行/需多卡），不自行采集基线数据
  - 若模型不可运行，记录具体原因和缺失项
输出:
  - 使用 .agents/skills/model-infer-optimize/templates/progress_template.md 创建 {model_dir}/agentic/progress.md，将分析结果写入常驻区（模型信息、并行策略、进度概览）
```

#### 0.3 分析确认与状态分流

主 agent 呈现分析结果和待决事项，按模型状态确定路径：

- **a. 模型可运行** → 进入 0.4 采集基线
- **b. 模型无法运行（代码缺失或适配不完整）** → 进入 0.4 框架适配
- **c. 模型需多卡才能运行（单卡显存不足）** → 按 0.4 路径 c 准备代码，完成 0.5 后进入阶段 1

#### 0.4 框架适配与基线建立

根据 0.3 确定的路径派发 implementer：

本轮新增或修复部署代码且已跑通时，先由 reviewer 按阶段 0 的基线范围验收代码与采集结果，再接收基线；已有有效验收可复用。需多卡的代码随阶段 1 验收。

**路径 a（模型可运行）**：

```
必须使用 skill: model-infer-migrator
工作目录: {model_dir}
部署模式: {框架部署 / 独立部署}
任务: 部署基线采集
```

implementer 返回后，将 baseline_metadata.json 摘要和精度参照写入 progress.md 常驻区，再进入 0.5。

**路径 b（模型无法运行）**：

```
必须使用 skill: model-infer-migrator
工作目录: {model_dir}
部署模式: {框架部署 / 独立部署}
任务: 框架适配 + 部署基线建立
模型来源: {HuggingFace 链接 或 本地路径}
权重路径: {如已知}
```

implementer 返回后：
- 若输出 baseline_metadata.json → 将摘要和精度参照写入 progress.md 常驻区 → 进入 0.5
- 若标记"需多卡" → 记录尚无运行基线 → 进入 0.5，再进入阶段 1

**路径 c（模型需多卡部署）**：
- 若已有框架适配代码 → 进入 0.5，再进入阶段 1；首个性能基线在多卡运行与精度验收后建立
- 若尚未完成框架适配 → 先按路径 b 派发 migrator 准备 modeling、configuration、YAML 和模型注册，作为并行化改造的基础；标记"需多卡"后进入 0.5，再进入阶段 1

#### 0.5 量化候选确认与方案初评估

> 本步骤属于阶段 0 的扩展分析，只评估量化方案，不修改代码。
> 量化初评估结论作为后续并行、融合、图模式和量化改造的参考输入。
> 首次完成或跳过本步骤后，目标部署需要并行适配或策略调整时进入阶段 1，否则进入阶段 2；后续阶段补做初评估时，完成后返回调用位置。

阶段 0 完成模型分析、且模型代码具备可读的框架适配基础后，按用户意向决定是否评估新增或变更的量化方案；意向不明确时由主 agent 确认。阶段 1–3 沿用当前有效部署路径，量化改造在阶段 4 实施。

1. 若用户不启用量化，记录决策，跳过 0.5 和阶段 4。
2. 若用户启用量化，继续确认是否已有 `quant_export_dir`。
3. 若已有量化产物，取得 `quant_export_dir`，进入量化方案初评估。
4. 若尚无量化产物，记录“量化产物未交付”，跳过 0.5 和阶段 4；用户后续交付 `quant_export_dir` 后，可从 0.5 重新进入量化方案初评估。在产物返回前，主流程不得进入量化改造。

`quant_export_dir` 是 infer 侧消费的上游量化产物目录，不是模型工作目录；它可以来自用户已有产物、AMCT 或其它量化产物生成流程的输出。

主 agent 提供量化产物目录，具体产物契约由 `model-infer-quantization` 检查；缺关键交付物时先交付补充诉求。

派发 model-infer-analyzer：

```
工作目录: {model_dir}
必须使用 skill: model-infer-quantization
任务: 量化方案初评估
量化产物目录: {quant_export_dir}
分析内容:
  - 检查量化产物契约、结构匹配、接入分级和部署形态估算
  - 按模型结构判断，不按模型名称套用参考
  - 不修改模型代码，不采集基线
  - 若契约不满足，输出量化算法或产物契约补充诉求
```

主 agent 执行：

1. 若量化初评估报告明确“无法安全接入”“需补充量化产物契约”或“建议暂不量化”，记录补充诉求，后续阶段沿用当前有效部署路径。
2. 若量化初评估报告明确可接入，写入 progress.md 常驻区，至少包含契约结论、结构指纹、接入分级、关键映射、显存/部署判断、对后续阶段的影响；若评估显示量化后可能收敛卡数，只作为并行决策输入，不在本步骤修改代码。
3. 向用户确认是否保留量化改造候选；若保留，则后续阶段在做并行、融合、图模式决策时参考该量化信息。

### 阶段 1：并行化改造

> 目标部署为单卡，或现有并行配置已满足目标且无需改造时，跳过本阶段。并行策略影响后续的通信组、TP 切分和 EP 路由，调整应先于 KVCache/FA 改造完成。
> 阶段 0.5 的量化初评估只作为显存、卡数和后续量化候选的参考输入。

#### 1.1 确认部署需求

沿用已明确的部署需求，缺失或有变化时确认：

1. **部署卡数和节点配置**：总卡数、每节点几卡（影响 TP 上限）
2. **目标场景**：高吞吐 / 低时延 / 均衡
3. **实际序列长度**：作为 KVCache 显存和 CP 适用性分析的输入
4. **batch size 需求**（如有）

将部署需求与阶段 0 的模型、硬件和量化初评估交给 analyzer，按实际分片、每 rank 显存和框架约束判断可行性；当前部署与候选量化方案的估算分别列出。

#### 1.2 启动分析 subagent

派发 model-infer-analyzer：

```
工作目录: {model_dir}
必须使用 skill: model-infer-parallel-analysis
任务: 并行策略分析（至少包含以下内容）
部署需求:（填入 1.1 确认的结果）
分析内容:
  - 提取模型参数和模块链路
  - 基于单套 parallel_config 分析整体并行策略，结合目标场景权衡 Prefill/Decode
  - 定量估算（显存、通信量），确定 parallel_config 具体值
  - 输出推荐方案及有实际取舍的备选，说明部署可行性和依据
```

#### 1.3 方案确认

呈现推荐配置、依据和待决事项，按「方案确认」处理：

1. **整体并行策略**：纯 TP / MoE EP / 模块级差异化并行？
2. **各模块 TP 度**：attn_tp / dense_tp / moe_tp / embed_tp / lmhead_tp / oproj_tp
3. **长序列附加配置**：是否引入 CP 及所需适配？

方案确认后进入实施。

#### 1.4 启动实施 subagent

派发 model-infer-implementer：

```
工作目录: {model_dir}
必须使用 skill: model-infer-parallel-impl
部署模式: {框架部署 / 独立部署}
任务: 并行化改造（至少包含以下内容）
阶段要点:
  - 按已确认的 parallel_config 实施
  - 覆盖选定配置涉及的通信组、并行层、Embedding/LMHead、YAML 和权重处理
自验证:
  - 适用的编译检查通过，多卡推理正常，输出符合已确定的验收口径
  - 实施记录写入 progress.md 工作区
```

#### 1.5 启动验证 subagent

派发 model-infer-reviewer：

```
工作目录: {model_dir}
部署模式: {框架部署 / 独立部署}
任务: 并行化改造后验证
验证内容:
  - 精度: 运行多卡推理，与已确定的精度参照对比；缺失时参考 model-infer-precision-debug 的「建立对比基准」
  - 性能: 已有运行基线时对比 Prefill 耗时和 Decode 单步耗时；首次跑通时记录当前实测值
  - 结果写入 progress.md 工作区（精度验证 + 性能验证 section）
检查项:
  - parallel_config 各参数已正确实施（YAML 配置与代码一致）
  - 各请求的输出符合精度判据，参与计算的 rank 无运行异常
```

#### 1.6 阶段总结

若阶段 0 标注"无基线"（模型需多卡才能运行），多卡运行与精度验收通过后，先派发 model-infer-implementer 采集首个性能基线：

```
必须使用 skill: model-infer-migrator
工作目录: {model_dir}
部署模式: {框架部署 / 独立部署}
任务: 部署基线采集
```

将 baseline_metadata.json 摘要和测试条件写入常驻区，作为后续累计收益的原始基线。首次跑通的并行阶段只记录当前实测结果；完成后按「共通验证与阶段收口」处理。

### 阶段 2：KVCache 静态化 + FA 算子替换

> 本阶段负责把 migrator 输出的过渡骨架升级到 KVCache + FA 目标路径。具体选型由 analyzer 输出，详见 `docs/design/kv_cache_design.md` 与 model-infer-kvcache skill。
> 后续阶段 3 的融合算子优化专注于 Attention Core 之外的模块。

#### 2.1 启动分析 subagent

派发 model-infer-analyzer：

```
工作目录: {model_dir}
部署模式: {框架部署 / 独立部署}
必须使用 skill: model-infer-kvcache（关注第一层快速选型 + 第二层数据结构与算子）
任务: KVCache 模式分析和选型
分析内容:
  - KVCache 布局与 FA 算子选型
  - 每个 cache 的 attn_type，是否启用 MLA absorb 或多 attn_type 混合
  - 估算块数 / 单卡显存占用
```

#### 2.2 方案确认

呈现选型、依据和待决事项，按「方案确认」处理：

1. KVCache 模式
2. 每个 cache 的 attn_type
3. MLA absorb 路径（仅 MLA 模型）
4. FA 算子与 layout 选型

方案确认后进入实施。

#### 2.3 启动实施 subagent

派发 model-infer-implementer：

```
工作目录: {model_dir}
部署模式: {框架部署 / 独立部署}
必须使用 skill: model-infer-kvcache（关注第三层实施流程对应大节）
任务: 阶段 2 KVCache + FA 改造（至少包含以下内容）
阶段要点:
  - 按已确认方案实施：cache 声明 → attention forward 改造 → metadata 消费
自验证:
  - 适用的编译检查通过，推理正常，输出符合已确定的验收口径
  - 实施记录写入 progress.md 工作区
```

#### 2.4 启动验证 subagent

派发 model-infer-reviewer：

```
工作目录: {model_dir}
部署模式: {框架部署 / 独立部署}
任务: KVCache + FA 改造后验证
验证内容:
  - 精度: 运行推理，Prefill/Decode 输出与基线对比
  - 性能: 运行推理，对比改造前后的 Prefill 耗时和 Decode 单步耗时
  - 结果写入 progress.md 工作区（精度验证 + 性能验证 section）
检查项:
  - KVCache 模式选型、静态化实现及 FA 算子替换已完成
  - Prefill 和 Decode 阶段缓存逻辑差异已正确处理
```

#### 2.5 阶段总结

按「共通验证与阶段收口」处理。KVCache/FA 精度异常交 implementer 使用 `model-infer-precision-debug` 定位修复；需要更换 KVCache 方案时，回到 2.1 选型、2.2 确认。

### 阶段 4：量化适配改造

> 本阶段在融合算子改造后、图模式适配前执行。图模式应尽量捕获最终 dtype、layout、kernel 和 cache 路径，因此量化改造优先先于图模式完成。
> 若阶段 0 未提供量化产物或用户暂不启用量化，则跳过本阶段进入图模式适配。
> 本阶段只接入已交付的量化方案和权重，不重新设计上游量化算法，不擅自扩展未确认的量化路线。
> 本阶段严格按既定量化方案和量化权重验证，不因报错擅自修改量化方案；若融合算子不支持量化，按用户确认的回退原则处理。
> 只有用户接受本轮量化实测结果后，新量化路径才作为阶段 5 输入；否则沿用改造前的有效路径。

#### 4.1 量化接入前变更复核

本步骤只判断模型或量化产物的变化是否影响量化初评估结论，不重做完整初评估。主 agent 先读取量化初评估报告：

- 若量化初评估报告缺失或已过期，回到 0.5 重新做量化方案初评估，不在本步骤补做完整分析。
- 若量化初评估报告可用，派发 model-infer-analyzer 做轻量变更复核：

```
工作目录: {model_dir}
必须使用 skill: model-infer-quantization
任务: 量化接入前变更复核
量化产物目录: {quant_export_dir}
分析内容:
  - 复核初评估以来模型或量化产物的变化对接入的影响
  - 聚焦权重加载、runtime object、模块前缀、dtype/layout/cache、post-load 和融合回退决策
  - 若无影响，明确沿用量化初评估结论
  - 不重做完整初评估，不修改模型代码，不采集基线
```

若变更复核明确不满足量化条件，输出阻塞点和补充诉求，按已有授权或用户决策跳过量化进入阶段 5，或暂停等待补齐。

#### 4.2 改造前用户决策

主 agent 基于量化初评估报告、变更复核结论和量化前最新基线，呈现当前方案与融合回退项，按「方案确认」处理。

若用户暂不量化或选择保留融合并跳过量化，记录原因，跳过到阶段 5。
若用户选择停止并补量化方案，输出阻塞点、融合量化需求和产物契约诉求，不继续后续阶段。
若用户确认继续量化改造，进入实施。

#### 4.3 启动实施 subagent

仅当用户选择“继续量化改造”时派发 model-infer-implementer：

```
工作目录: {model_dir}
必须使用 skill: model-infer-quantization
任务: 阶段 4 量化适配改造与量化权重加载
量化产物目录: {quant_export_dir}
量化前最新基线: {latest_baseline}
阶段要点:
  - 按用户确认的量化路线接入配置、权重、runtime 映射和 post-load 处理
  - 严格使用既定量化方案和量化权重，不因报错修改 target / ignore / 张量语义
  - 若融合算子不支持量化，按用户确认的回退原则处理，并记录清单
  - 获取量化部署基线；若量化后单卡可满足，按确认部署口径验证
自验证:
  - 量化模型可加载，Prefill / Decode 跑通，输出可读且有量化路径生效证据
  - 融合算子回退清单、原始错误和后续融合量化需求已记录
```

#### 4.4 启动验证 subagent

派发 model-infer-reviewer：

```
工作目录: {model_dir}
任务: 阶段 4 量化适配验证
验证内容:
  - 量化权重确已加载，且日志或状态文件能证明量化路径真实生效
  - Prefill / Decode 至少各跑通一次，输出符合已确定的验收口径
  - 精度: 运行推理，对比量化前后的输出可用性和关键误差
  - 性能: 运行推理，记录量化部署基线；与非量化基线和量化前最新基线对比
  - 按已确认的量化部署配置验证；卡数变化时单列部署收益及测试条件
检查项:
  - 每个量化模块均有生效证据
  - 回退到原有非融合算子的模块已显式记录
  - 无擅自修改量化方案、target、ignore 或权重张量语义的行为
  - 量化初评估报告和量化接入前变更复核结论中的冲突项已给出处理方式
```

#### 4.5 实测后用户决策与阶段总结

修复与性能异常处理按「共通验证与阶段收口」执行；量化性能未达预期时，还应核对量化路径是否真实生效。主 agent 基于实测结果呈现后验取舍，按授权或用户决策处理：

- 接受当前量化方案 → 将量化部署基线、量化后部署口径、融合算子回退清单作为阶段 5 图模式适配输入
- 跳过量化 → 记录跳过原因和实测收益；进入阶段 5 前将运行配置和代码恢复到本轮量化改造前的有效路径
- 修正量化方案后迭代 → 记录阻塞点和补充诉求，等待新量化产物后回到 4.1 复核

汇总改造方案、问题及解决方案、融合算子量化需求和收益结论，按共通规则收口。
